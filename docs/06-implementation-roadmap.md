# 06 - خارطة الطريق التنفيذية

## المرحلة 0 - التأسيس والتوثيق (الحالي)
- إغلاق نطاق المشروع وقيود الـ MVP.
- توقيع مسؤوليات Backend vs Frontend.
- اعتماد نموذج البيانات.
- اعتماد استراتيجية الفروع والدمج.

## المرحلة 1 - قاعدة المشروع
- إنشاء حلول .NET وAngular (بدءً لاحقًا).
- إعداد Auth + الصلاحيات الأساسية.
- إعداد الاتصال مع SQL Server للبيانات الداخلية (غير مصدر ZKTime بعد).
- إعداد SignalR Hub الأساسي.

## المرحلة 2 - بنية الإنتاج وتعيين العمال
- CRUD للخطوط، المراحل، العمال.
- تعيين ثابت.
- خريطة جاهزية بسيطة مع الحساب الأساسي.
- لوحة إشعارات أولية.

## المرحلة 3 - التعيين المؤقت وغياب
- drag & drop تفاعلي.
- منطق بدء/إنهاء تعيين مؤقت.
- سياسة الرجوع لتعيين ثابت.
- سيناريوهات غياب وتغطية.

## المرحلة 4 - استقرار وتجارب
- تحسين تنبيهات مباشرة.
- اختبارات تكامل أساسية.
- تحسين الأداء للموبايل.
- توحيد UX (sidebar، breadcrumb، ألوان الحالات).

## معايير القبول (DoD) لكل مرحلة
- كل endpoint مستخدم له اختبارات قبول وظيفية.
- الحالة اللونية واضحة دون غموض.
- التغيرات اللحظية لا تتطلب إعادة تحميل كامل الصفحة.
- لا وجود لتناقض منطقي في تعيين المؤقت.

## استراتيجية الفروع المقترحة
- `main` : branch الإنتاج/المراجع المستقر.
- `docs/project-foundation` : إعداد التوثيق الحالي.
- فروع لاحقة:
  - `feat/backend-foundation`
  - `feat/frontend-foundation`
  - `feat/assignments`
  - `feat/readiness-map`

## مخاطر واحتياطات
- مخاطر التكامل مع ZKTime:
  - اختلاف صياغة الحقول الزمنية.
  - تأخير في التحديث اللحظي.
- مخاطر UX موبايل:
  - تعقيد drag & drop.
- مخاطر صلاحيات:
  - وصول Admin لإعدادات حساسة.
- mitigation:
  - توحيد نماذج DTO من البداية.
  - جلسات مراجعة UX في كل مرحلة.
  - قائمة تحقق أذونات واضحة قبل الدمج.

## أسئلة مفتوحة
- هل يجب اعتماد خريطة المصنع كرسم شبكي من اليوم الأول أو نسخة قائمة قابلة للتوسع؟
- هل يوجد رقم SLA لتأخير التحديث اللحظي المقبول؟
- هل نبدأ بخريطة تنبيه global أم per-line فقط؟
