# 02 - مسودة البنية المعمارية

## النظرة الكلية
نظام Layered/Modular على شكل:
- **Web App (Angular + PrimeNG)** واجهة موبايل أولًا.
- **Backend API (.NET Core)** يملك منطق الأعمال والضبط.
- **SignalR Hub** للتحديثات اللحظية.
- **مصدر حضور خارجي (ZKTime SQL Server)** كـ reader feed.

## تدفق البيانات
1. العامل يقوم بعملية دخول/خروج في نظام الحضور الخارجي.
2. الواجهة/الخدمات تتلقى حالة اللحظية عبر API/Job.
3. API يحدث Ready State على المراحل.
4. SignalR ينشر التغييرات للعمليات العاملة.
5. المستخدم يرى الألوان والنسب فورًا.

## مكونات Backend المقترحة
- **AuthModule**: المستخدم، الأدوار، الصلاحيات.
- **ProductionModule**: خطوط، مراحل رئيسية، مراحل فرعية.
- **WorkerModule**: العمال، الحضور، التخصيصات.
- **AssignmentModule**: تعيين ثابت + مؤقت.
- **NotificationModule**: SignalR + read/unread state.
- **ReadinessModule**: حساب النسب وتجميع الحالات.
- **IntegrationModule**: جلب بيانات ZKTime (بدون الاتصال في هذه المرحلة).

## حدود المسؤليات
- Backend يتولى:
  - التحقق من سياسات التعيين.
  - حساب التجميعات والنسب.
  - إدارة زمن التعيين المؤقت.
  - بث الأحداث عبر SignalR.
- Frontend يتولى:
  - عرض التفاعل.
  - إدارة حالة واجهة المستخدم المحلية.
  - استهلاك أحداث SignalR وتحديث العناصر.

## استضافة وإدارة البيئة (للمستقبل)
- بيئة تنفيذية واحدة في البداية (Single App + Single DB) أفضل للـ MVP.
- فصل واضح لطبقات القراءة/الكتابة إذا توسع النظام.
- إعداد Branch Strategy:
  - `main` ثابت.
  - فروع ميزة واضحة: `feature/<area>`.
  - مراجعة قبل دمج أي تغيير إلى `main`.

## قرارات تصميم متقدمة/مخففة
- تجنب الميكرو سيرفس الآن.
- لا حاجة لبناء DSL أو محرك قواعد معقد.
- احتفاظ بواجهات API بسيطة وموثوقة.

## أسئلة مفتوحة
- هل سيتم عرض الخريطة على هيئة رسم بياني (Tree/Grid) من البداية أم تبسيطها إلى قائمة قابلة للتوسع؟
- هل يحتاج المشروع لنسق Multi-tenant أو مصنع واحد فقط؟
- هل نحتاج آلية مزامنة pull فقط أم push + poll مع fallback؟
- هل ستدعم لوحة التحذيرات أكثر من مستويين (تحذير/عاجل)؟
